# IMECE 실험 기록

이 문서는 실제로 실행된 내역, 보존된 데이터, 해당 산출물의 분석 방법, 그리고 보존된 증거로 뒷받침할 수 있는 논문용 주장을 기록합니다.

이 파일의 용도:
- 보존된 배치(batch) 전체 이력 확인
- 보존된 증거에서 사용된 정확한 조건(condition) 및 프롬프트 설정 확인
- 기계가 생성한 요약과 이를 해석하는 방법
- 논문에서 사용 가능한 안전한 결과(paper-safe result) 및 현재의 한계점 확인

[`implementation-kor.md`](./implementation-kor.md)는 여전히 규범적(normative) 규격입니다.
두 문서 간에 차이가 발생할 경우, 이 파일은 보존된 실제 기록을 설명하며 `implementation-kor.md`는 원래 의도된 규칙을 설명합니다.

## 1. 보존된 증거 범위 (Preserved Evidence Boundary)

다음 보존된 배치들이 현재 논문에 사용될 수 있는 증거입니다:

| 배치 ID | 페이즈 의미 | 보존 목적 | 산출물 루트 |
| --- | --- | --- | --- |
| `discovery-20260331` | 디스커버리 파일럿 | `C2`가 필요한지, 그리고 어떤 헬퍼를 고정(freeze)할 수 있는지 결정 | `artifacts/imece/discovery-20260331/` |
| `c2-freeze-t3-20260331` | 타겟팅된 `C2` 검증 | 고정된 `C2` 서브셋 하에서 아직 남아있는 `T3` 정사각형 패턴의 간극 검증 | `artifacts/imece/c2-freeze-t3-20260331/` |
| `official-sim-001` | 공식 시뮬레이션 평가 | 최종 `T1-T4` 태스크 세트에서 `C0`, `C1`, `C2` 전면 비교 | `artifacts/imece/official-sim-001/` |

이들만이 현재 논문에서 직접적인 증거로 인용할 수 있는 보존된 배치들입니다.

삭제된 임시적인(ad hoc) 실행이나 폐기된 내부 실행 결과는 논문을 위한 주장의 일부가 될 수 없으며, 이를 바탕으로 표나 데이터를 재구성해서는 안 됩니다.

## 2. 기계가 생성한 분석 결과

보존된 각 배치에는 다음 파일들이 포함되어 있습니다:

- `analysis.json`
  - 현재 채점 기준 하의 배치 요약
  - 헬퍼 고정(freeze) 리뷰
  - 태스크 성공 요약
- `audit.json`
  - 과거의 인터페이스 불일치 발생 건수
  - 구버전 룰과 현행 룰 간의 태스크 성공 불일치(drift)
  - 재현성 메타데이터 커버리지

보존된 배치들 간의 주요 차이점:
- 보존된 디스커버리 배치는 최상위 런타임 메타데이터 캡처 체계 이전에 구축되었습니다.
- 보존된 `c2-freeze-t3-20260331` 배치는 온전한 개별 `runtime_metadata`를 가지고 있습니다.
- 보존된 `official-sim-001` 배치는 온전한 개별 `runtime_metadata`를 가지며 과거의 인터페이스 불일치 오염이 없습니다.

## 3. 현재 연구 요약

### 조건 (Conditions)

- `C0`: 일반(generic) ROS-MCP 베이스라인
- `C1`: 기존 인터페이스에 작동 규칙 관련 프롬프트만을 추가한 조건
- `C2`: 베이스라인 인터페이스에 국소적이고 고정된 최소 헬퍼 서브셋을 적용한 조건

### 태스크 (Tasks)

- 시뮬레이션:
  - `T1`: 이륙, 호버링, 착륙 (Takeoff Hover Land)
  - `T2`: 짧은 이동 (Short Translation)
  - `T3`: 정사각형 비행 패턴 (Square Pattern Flight)
  - `T4`: 비행 중 인터럽트 처리 (Mid-flight Interrupt Handling)
- 계획된 실제 비행:
  - 오직 `C2`만 적용
  - `T1-T4`
  - 각 태스크 당 `5`회 반복 (총 `20` 에피소드)
- 계획된 교육용 시뮬레이션 확장:
  - 오직 `C2`만 적용
  - `T1-T3`
  - 프롬프트 난이도: `elementary`, `middle`, `high`, `college`
  - 형제(sibling) 프롬프트: `a`, `b`, `c`
  - 총합 `36` 에피소드

### 변경 이력 참조 (Historical Note)

초기에 고려되었던 모호성 관련 테스트 태스크들은 폐기 조치 되었습니다.
보존된 최종 확정 맵핑은 다음과 같습니다:

- `T3 = Square Pattern Flight`
- `T4 = Mid-flight Interrupt Handling`

이 논문은 오직 이 최종 맵핑만을 사용해야 합니다.

## 4. 조건 기록 (Condition Record)

### C0

조건 아티팩트: [`config/imece/c0.md`](../../config/imece/c0.md)

에이전트가 받는 정보:
- 조건명
- 노출된 IMECE 도구만 사용하라는 지시
- 조작 이전에 허용된 ROS 표면 구조부터 탐색하라는 지시

왜 중요한가:
- `C0`은 실행 가능한 일반(generic) ROS 베이스라인입니다.
- 드론의 특화 환경을 사전에 잘 아는(drone-aware) 모델이 아닙니다.
- 아무 것도 볼 수 없는 무능한 맹목적 조건도 아닙니다.

### C1

조건 아티팩트: [`config/imece/c1.md`](../../config/imece/c1.md)

추가되는 지식 프롬프트:
- 로컬 위치 축은 `ENU`를 사용합니다.
- 모드 전환 이전에 `OFFBOARD` 모드는 셋포인트 사전 전송(prestream)이 필수적입니다.
- 비행 중에는 셋포인트 데이터 스트리밍이 지속되어야 합니다.
- 모호함이 있을 때는 짧은 확인 질문을 유도해야 합니다.
- 최종 착륙 시에는 `LAND` 모드를 지향해야 합니다.

왜 중요한가:
- `C1`은 오로지 프롬프트 지식 안내만으로 복구를 시도하는 가장 작은 개입 단위입니다.
- `C1`만으로 모든 실패 문제가 해결되었다면, 더 나아간 `C2`의 설계는 정당화되지 않았을 것입니다.

### C2

조건 아티팩트:
- [`config/imece/c2.md`](../../config/imece/c2.md)
- [`config/imece/c2_freeze.json`](../../config/imece/c2_freeze.json)

현재 고정(freeze)된 헬퍼 서브셋:
- `setpoint_relay`
- `mode_guard`
- `abort_watchdog`

중요한 요건 및 제한 사항:
- `frame_guard` 코드는 시스템에 있지만 현재 고정된 서브셋에는 포함되지 않았습니다.
- 보존된 디스커버리 감사 로그를 보면, 현재 분류기 기준 하에서 치명적인 프레임/부호 불일치 모순 에러가 계속 반복하여 발생하지 않았기 때문입니다.

논문에서 `C2`를 표현할 때 사용하는 안전한 접근:
- 얇게 고정된 로우 레벨 지원 수준 헬퍼 서브셋 
- 비행체 API 수준의 시맨틱(semantic) 레이어가 아님
- 미션 플래너 계층이 아님

## 5. 왜 `C0 -> C1 -> C2` 구조로 설계되었는가

이 단계적 조건 디자인 방식은 추상적으로 결정된 것이 아닙니다. 오직 보존된 디스커버리 기록 로그에서 나타난 특징적 진단 흐름에 근거해 세워진 조치입니다.

| 조건 | 보존된 로그상 실제 증거 | 설계가 담고 있는 의미 |
| --- | --- | --- |
| `C0` | [`C0/T1/episode-01/metrics.json`](../../artifacts/imece/discovery-20260331/C0/T1/episode-01/metrics.json)은 44번의 일반 툴 콜과 고작 9번의 셋포인트 성공. 이후 한계 고도 도달 역시 `max_altitude_m = 0.0245`로, 오프보드 기만 거부 `4`건 달성 후 타임아웃 오류 밑 워치독 경보 등으로 처참하게 마감됨. | 베이스라인 `C0`은 최소한 어떻게 다뤄야 하는지조차 모르는 백지 환경을 막아내기 위해, 일단 일반적 통용 ROS 제어 인터페이스 환경만 열어주어서 맹인 상태 셧다운을 방어한 환경입니다. |
| `C1` | [`C1/T1/episode-02/gemini.jsonl`](../../artifacts/imece/discovery-20260331/C1/T1/episode-02/gemini.jsonl) 프롬프트 투여자료를 학습 받은 모델은 알아서 사전 셋포인트 전송 지향과 지속 스트리밍 구사를 이치에 맞게 스스로 계획합니다. 그러나 실행 상 오류 로그에선 구 구동 스키마 버전 오류 단절 문제(`wait_for_previous`) 이탈이 나며 여러 초 동안 달랑 1건(`published_count = 1`)만을 출력 보고합니다. 이로써 `metrics.json`은 에피소드 전체 통틀어 `setpoint_count = 4`, `max_altitude_m = 0.0291`로 처참하게 남았습니다. | `C1`은 논리적 추론 능력이 올바르다 해도, 저수준의 기반 메커니즘을 제대로 다루지 못해 망가지는 상황을 여실히 보여주는, 가장 좁게 제한된 '사전 프롬프트 정보 전용' 제어군입니다. |
| `C2` | 디스커버리가 오직 `setpoint_relay`, `mode_guard`, `abort_watchdog` 헬퍼 종류만 고정합니다; 좁혀진 `C2:T3`가 정사각형 패턴 시도 중 한계 남은 간극을 치유 복원 검증합니다. 결국 `C2`는 소수의 성공 요건 위반만 남긴 채 악성적이던 `F1-F5` 통신 장애 등 파국 패턴을 통과하여 대부분 문제를 해소합니다. | `C2`는 의미론적 미션 치 제어가 아니라, 전송과 안전성에만 방점을 두어 지원하는 얇은 수준의 헬퍼 레이어 입니다. |

실제 논문상으로 대두될 주요 가치 내용 3가지:
- `C0`는 적어도 완전 맹인이 아니게 일반적 ROS 제어와 연결 기반 탐색 제어는 포함하게 줍니다. 실행 환경의 유지를 위해서입니다.
- `C1`은 무제한적인 프롬프트 최적화 대회가 아니라, 단지 프롬프트 만으로 수리할 때 어느정도 효과를 갖는지를 정립한 개선 확인용의 최소 수리 세트입니다.
- 디스커버리 분석 과정에서 이런 순수 프롬프트 보정 만으로는 본연의 구동 치 타이밍 장구 나 고질적 통신 단절 한계 수복 자체가 안됨을 파악했기에 그제서야 아주 최소한의 치유 도구 서브셋 단위 헬퍼 체제로 한정해서 묶은 것이 `C2` 라는 점입니다.

보존된 `C1/T1/episode-02` 의 전파 기록 흔적은 대체 왜 `C1` 단계를 거쳐 `C2` 로 나아가는지의 강한 정당성 입증 근거입니다. 모델 자신이 스스로 통신 궤도 유지와 안정 전파 산출 구조를 이해하고 논리에 맞게 진행하나 결과를 보면 에러와 고갈이 냅니다. 그러므로, 이 결과가 도출한 결론은 다음과 같습니다:
- `C1`은 운영적 추론을 더 낫게 만들었습니다.
- 그러나 `C1`은 저레벨 수준 메커니즘을 확실하게 견고히 복구하지 못했습니다.
- 따라서 남겨진 수송 체제 전송, 타이밍 그리고 안전 보수 망 회피성 실패 에러들이 곧 소규모의 필수 헬퍼군 집합인 `C2` 의 도입 및 유지를 옹호하게 되었습니다.

## 6. 조립된 프롬프트 체계 (Prompt Assembly and Task Prompt Record)

첫 번째 턴의 프롬프트는 [`ros_mcp/imece/config.py`](../../ros_mcp/imece/config.py) 에서 다음 순서로 조립됩니다:

1. 공유 계약(Shared contract)
2. 조건(Condition) 아티팩트
3. 만약 조건이 `C2`라면 `C2` 관련 헬퍼 안내 블록
4. 지원되는 경우 태스크 전용의 실행 요구 조항 블록
5. 에피소드 관련 메타데이터 정보들
6. 정식(Canonical) 태스크 프롬프트

각 에피소드는 이 당시 전달받은 내용 텍스트 전체를 `prompt.txt` 로 각각 보존하기에 매우 중요합니다.

### 고정 유지된 공유 계약 (Shared Contract Held Constant)

보존된 모든 실행 전반에 걸쳐 첫 번째 턴 프롬프트 구조에 고정 유지되는 공유 요건:
- 노출된 허가 API 인 IMECE 도구들만 단독으로 제어 사용할 것
- 만약 모호한 구제가 필요할 땐 한 가지의 짧은 질의 응답 요청 구조를 낼 것
- 시스템상 거듭나기 힘들다면 가벼이 거부의사를 밝힐 것
- 모든 턴 통신의 마지막은 `CLARIFY: ...`, `REFUSE: ...`, 그리고 업무 완수의 `DONE: ...` 단 3개 구조 중 하나만 택할 것

### 태스크 프롬프트 기록구

| 태스크명 | 타이틀 | 정식 프롬프트(Canonical prompt) | 주요 실험 고정 태스크 세팅값 |
| --- | --- | --- | --- |
| `T1` | 이륙, 호버링, 착륙 | `Take off to one meter, hover for five seconds, then land.` | 별도의 태스크 실행 요구 조항 블록이 없음 |
| `T2` | 짧은 전면 이동 | `Take off, move one meter forward, hover, and land.` | 반드시 고정된 2회의 방향 조치 (이륙 후 정지, 1미터 전진 이동 조치) 타겟 목표를 조달할 것 |
| `T3` | 사각형 경로 비행 | `Take off, fly a square with one-meter sides, return near the start, and land.` | 반드시 시작점을 국지 기준점으로 삼아 차출 파생된 5회에 걸친 움직임 통제 전파 조치를 도입할 것 |
| `T4` | 비행 중 인터럽트 처리 | `Take off and move forward one meter.` | 첫 번째 턴 시에는 무조건 `CLARIFY` 도출, 그리고 두번째에 결정론적 제어로 개입 보정을 함 |

실험 내내 추가 고정되어 지속 유지된 태스크별 통제 기준들:
- `T2`
  - 정확히 `2`번의 목표 지향점을 발부해야 함
  - 첫 이륙 이후 고정 고도가 확보되기 전까지는 목표를 바꿔 잡지 말 것
- `T3`
